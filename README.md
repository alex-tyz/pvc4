# Лабораторная работа №4 — FreeRTOS, вариант 2 «Компас»

Продолжение предоставленной ЛР3 (`PVS3_FULL.zip`) для **SDK‑1.1M / STM32F427VIT6**.
Сохранены дисплей SSD1306 128×64, сброс через PCA9538, магнитометр LSM9DS1/LSM9DS0,
распиновка, ориентация осей, масштабные коэффициенты и протокол ЛР3. Клиент ПК перенесен без изменений.

## Что реализовано

- Три вытесняемые задачи FreeRTOS 10.6.2: дисплей, магнитометр, обмен с ПК.
- Дисплей: период 40 мс (цель 25 кадров/с), стрелка, X/Y/Z в мГс, коэффициенты, счетчик `00…99` справа внизу.
- UART6: прием в прерывании, очередь FreeRTOS, передача по прерыванию с блокировкой только задачи связи.
- Коэффициенты 0–200 %, исходно 100 %. Команда изменяет все три одновременно; действуют до следующей команды или сброса питания.
- Mutex с наследованием приоритета защищает общую шину I2C; очереди длины 1 передают целостные снимки данных.
- `STATS` и утилита проверки кадров под нагрузкой; тесты расчета и протокола; сборка в GitHub Actions.

**Статус:** прошивка проверяется кросс-сборкой, логика — автоматическими тестами.
Физический стенд в этой среде не подключен: частоту кадров, направление осей и работу периферии необходимо подтвердить на устройстве.
Настроенный период 40 мс сам по себе не является измерением FPS.

## Импорт, сборка и прошивка в STM32CubeIDE

1. Клонировать репозиторий в удобный каталог, например `C:\STM32\pvc4`.
2. **File → Import → General → Existing Projects into Workspace**; выбрать каталог `PVS4` и импортировать проект `PVS4`.
3. **Project → Build Project**, конфигурация Debug. Драйвер I2C и ядро FreeRTOS уже включены: дополнительная генерация CubeMX не требуется.
4. Подключить стенд через USB DBG. **Run → Debug Configurations → PVS4 Debug** использует конфигурацию FTDI/OpenOCD из ЛР3. При необходимости выбрать доступный в IDE OpenOCD.
5. Запустить отладку, после остановки в `main` нажать **F8 / Resume**.

Проект поддерживается в исходниках, с native API FreeRTOS. `docs/lab3_reference/hardware_lab3.ioc` — только исходная конфигурация аппаратуры из ЛР3;
она **не является проектом генерации ЛР4**. Повторная генерация по ней восстановит bare-metal обработчики и исходные приоритеты.

Параметры платы: HSE 25 МГц, SYSCLK/HCLK 180 МГц, APB1 45 МГц, APB2 90 МГц;
I2C1 PB8/PB9 400 кГц; USART6 PC6/PC7 38400 8N1. SysTick — FreeRTOS, TIM6 — HAL.

### Если Set Active / Manage неактивны и показано `This project is not a CDT project`

В первой опубликованной версии проекта в `.cproject` была утрачена служебная строка CDT `<?fileVersion 4.0.0?>`.
Это ошибка метаданных проекта, которая не обнаруживается отдельной кросс-сборкой GCC.
Обновить проект из репозитория либо закрыть IDE и вставить эту строку между XML-декларацией и `<cproject ...>`:

```xml
<?xml version='1.0' encoding='UTF-8'?>
<?fileVersion 4.0.0?>
<cproject storage_type_id="org.eclipse.cdt.core.XmlProjectDescriptionStorage">
```

Сохранить файл и снова открыть STM32CubeIDE. Исправлять нужно `.cproject` именно импортированного проекта;
его каталог указан в **Properties → Resource → Location**. После обновления выполнить **Refresh**, при необходимости **Close Project → Open Project**.
Регрессионные тесты `test_project_metadata.py` теперь проверяют наличие этой инструкции и обеих конфигураций сборки.

## Сборка без IDE

Нужны Python 3 и Arm GNU Toolchain (`arm-none-eabi-gcc`, `objcopy`, `size`) в PATH:

```sh
python tools/build.py
```

Либо указать каталог инструментов:

```sh
python tools/build.py --toolchain C:/tools/arm-gnu-toolchain/bin
```

Результат: `build/PVS4.elf`, `.bin`, `.hex`, `.map`. Бинарный образ записывается с адреса `0x08000000`.
Готовые BIN/HEX находятся в `firmware/`; ELF и MAP также доступны как артефакт успешной сборки GitHub Actions.

## Клиент ПК

```sh
python -m pip install -r client/requirements.txt
python client/compass_client.py COM5
```

В Windows также можно запустить `client/run.bat`. Указать свой COM-порт.
Закрыть другие программы, использующие этот порт. Клиент отображает поле и стрелку, отправляет коэффициенты и ведет журнал.
Телеметрия остается раз в 200 мс, как в ЛР3; дисплей стенда обновляется независимо, раз в 40 мс.

## Проверка на стенде

1. Держать плату горизонтально, проверить X/Y/Z, стрелку и непрерывное изменение `00…99`.
2. Повернуть плату и поднести магнит. Направление осей проверить экспериментально; при необходимости изменить `COMPASS_SWAP_XY`, `COMPASS_SIGN_X`, `COMPASS_SIGN_Y` в `Core/Inc/compass_app.h`.
3. Отправить `200 100 0`: X должен удвоиться, Z обнулиться; коэффициенты сохраняются при последующих измерениях.
4. Закрыть клиент и измерить кадры без нагрузки и с 20 командами SCALE/с:

```sh
python tools/check_fps.py COM5 --seconds 30 --output measurements/idle.json
python tools/check_fps.py COM5 --seconds 30 --load-rate 20 --output measurements/load.json
```

Критерии утилиты: не менее 20 кадров/с на каждом интервале наблюдения, максимальный промежуток между успешными кадрами ≤50 мс,
без новых ошибок дисплея, UART и пропусков периода. Максимальный промежуток считается с включения; для независимого опыта перезагрузить стенд.
Сбой самого дисплея или общей шины I2C исключает гарантию кадров и отображается диагностикой.

## Автоматические тесты

```sh
mkdir build
gcc -std=c11 -Wall -Wextra -Werror -IPVS4/Core/Inc tests/test_logic.c PVS4/Core/Src/compass_logic.c -lm -o build/test_logic
./build/test_logic
python -m unittest discover -s tests -p "test_*.py" -v
```

В PowerShell исполняемый файл удобно назвать `build/test_logic.exe` и запускать `./build/test_logic.exe`.
Проверки не заменяют испытания на стенде. Источники и происхождение зависимостей: [THIRD_PARTY.md](THIRD_PARTY.md).
